# LISP: краткий референс по синтаксису

Документ для использования как референс при проектировании DSL с лиспоподобным синтаксисом.

## 1. Фундаментальная идея

Весь синтаксис LISP строится на **одной** структуре — **s-выражение** (sexp):

```lisp
(оператор операнд1 операнд2 ...)
```

Правила всего три:

1. Атом — это число, строка, символ/идентификатор или булево значение.
2. Список — это `( a1 a2 ... an )`, где каждый `ai` — атом или другой список.
3. Всё остальное — семантика, а не синтаксис: порядок элементов интерпретируется конкретным оператором.

Итог: **одна пара скобок**, никаких `{}`, `[]`, `<>` для разных конструкций. Парсер — это буквально чтение вложенных списков, а не стейт-машина на множестве разделителей.

## 2. Базовые элементы

### Атомы

```lisp
42          ; число
3.14        ; число с плавающей точкой
"строка"    ; строка в двойных кавычках
foo         ; символ (идентификатор), регистр обычно не важен
t / nil     ; истина / ложь (в Common Lisp); в Scheme — #t / #f
```

### Списки и вызовы

```lisp
(+ 1 2 3)           ; префиксная нотация: оператор первым
(if (> x 0) "pos" "neg")
(max 10 (min 3 7))  ; вложенность = вложенные списки
```

### Квотирование (важнейшая часть для DSL!)

```lisp
'(1 2 3)        ; апостроф = «не вычисляй, верни данные как есть»
'(a b c)        ; список данных, а не вызов функции
`(a ,b c)       ; backquote: шаблон; ,b — подстановка значения b
,@xs            ; splice: вставить элементы списка xs «вровень»
```

Квотирование — это механизм, который позволяет одним и тем же синтаксисом описывать и **код**, и **данные** (homoiconicity, гомоиконичность). Для DSL это ключевое свойство: дерево AST совпадает с текстом программы, и генерировать/трансформировать код так же просто, как манипулировать списками.

## 3. Специальные формы

«Операторы» с нестандартной семантикой вычисления — не функции, а особые конструкции:

```lisp
(if условие then else)           ; ветвление
(let ((x 1) (y 2)) (+ x y))      ; локальные привязки
(quote expr)  ≡  'expr           ; явная форма квотирования
(lambda (a b) (+ a b))           ; анонимная функция
(defun name (args) body)         ; определение функции (Common Lisp)
```

Принцип: синтаксически это те же списки — отличие только в семантике первого элемента. Парсер их не различает, это задача интерпретатора/компилятора.

## 4. Определение функций и переменных

```lisp
;; Common Lisp
(defun square (x) (* x x))
(defvar *counter* 0)        ; глобальная (соглашение: *earmuffs*)

;; Scheme / Clojure (похожие DSL-совместимые варианты)
(define (square x) (* x x))
(defn square [x] (* x x))   ; Clojure: квадратные скобки для аргументов — исключение из правила «одних скобок»!
```

Заметка для DSL: Clojure ввёл `[ ]` и `{ }` — это работает, но это именно та ступень, за которой начинается усложнение парсера и разнобой в стиле. Классический подход — всё через `()`.

## 5. Пары и точечная нотация (cons)

Внутри списки — это бинарные пары (cons cells):

```lisp
(cons 1 2)        ; → (1 . 2)  «точечная пара»
(cons 1 '(2 3))   ; → (1 2 3)
(car '(1 2 3))    ; → 1   (голова)
(cdr '(1 2 3))    ; → (2 3)  (хвост)
```

Пустой список: `nil` / `'()` — он же ложь в Common Lisp.

Для DSL: если список — всегда «первый элемент = роль/оператор, остальное — дети», можно обходиться без cons-ячеек вообще, но `car/cdr` показывают идиоматичный способ ходить по дереву.

## 6. Макросы — код как данные

```lisp
(defmacro when (cond &rest body)
  `(if ,cond (progn ,@body)))

(when (> x 0)
  (print "positive"))
```

Макрос — функция, которая получает **невычисленное синтаксическое дерево** (список) и возвращает новое дерево. Никакого отдельного синтаксиса для метапрограммирования — снова те же списки.

## 7. Правила чтения (грамматика в миниатюре)

```
программа    := форма*
форма        := атом | список
список       := '(' форма* '.'? форма? ')'   ; точка — только для cons-пар
атом         := число | строка | символ
символ       := [^()"'`,; \t\n\r]+
комментарий  := ';' до конца строки
строка       := '"' ... '"'  (экранирование через \)
```

Отдельные нетерминалы: `'x` → `(quote x)`, `` `x`` → `(quasiquote x)`, `,x` → `(unquote x)`, `,@x` → `(unquote-splicing x)`. Читатель (reader) раскрывает их **до** интерпретатора — это чисто синтаксический сахар.

## 8. Что взять для DSL — чеклист

1. **Одна пара скобок.** Каждый узел дерева — `(head child1 child2 ...)`. Парсер: рекурсивный спуск на один разделитель, ~30 строк кода.
2. **Префиксная нотация всегда.** `f a b c`, а не инфиксные выдумки — убирает проблему приоритетов операторов.
3. **Комментарий — один символ** до конца строки (`;` в Lisp, `#` у Clojure).
4. **Квотирование/шаблоны** — если планируете метапрограммирование или литералы сложных структур, встройте `'`, `` ` ``, `,` сразу.
5. **Семантику роли узла держите в `head`**, а не в новых скобках: `(if ...)`, `(loop ...)`, `(def ...)` — парсер не должен знать о них ничего.
6. **Не плодите скобки.** `[ ] { } < >` для «разных типов узлов» — путь к стейт-машине в парсере и неоднозначности. Если очень нужно выделить группу — это семантика, а не синтаксис.
7. **Точечные пары / cons** — опционально; обычный список достаточен для 95% DSL.
8. **Пустой список** — естественное «ничего»/нуль-узел.

## 9. Типовые ошибки при «изобретении своих скобок»

- **Разные скобки для разных конструкций** → парсер превращается в стейт-машину; при ошибке невозможно сказать, где «закрыть».
- **Инфиксные операторы** → нужны приоритеты, ассоциативность, отдельный Pratt-парсер.
- **Опциональные разделители** (запятые, точки с запятой) → грамматика становится неоднозначной.
- **Контекстно-зависимые ключевые слова** в синтаксисе (а не в семантике) → невозможно парсить без таблицы символов.
- Lisp-решение всех этих проблем: синтаксис **минимален и контекстно-свободен**, вся сложность — в обработчиках форм.
